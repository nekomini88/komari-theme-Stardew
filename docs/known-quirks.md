# 已知行为怪异清单（重构期间发现，**故意未修**）

来源：2026-10-14 重构时，为「先补测试再改」而新写的 422 条断言，在推导断言的过程中暴露出的
**真实古怪行为**。这些都不是重构引入的，而是原本就存在。

## 为什么当时不修

纯重构的铁律是**不夹带行为改动**：当时那 422 条断言的作用正是把「现有行为」钉死，
如果顺手改掉其中任何一条，重构的「零回归」就无法证明（测试同时被改了，等于既当运动员又当裁判）。
所以统一选择：**记录，不改**。

用户当时未就该问题给出指示，按最保守默认执行（即本文件）。

## 清单

1. **空串搜索返回全部，而不是空集合**
   `isRegionMatch(regionEmoji, '')` 恒为 `true`（因为 `'x'.includes('') === true`），
   导致 `searchRegions('')` 返回全部 258 个地区。未知 emoji 走
   `regionEmoji.toLowerCase().includes(term)` 裸包含分支时同样被空串命中。
   → 影响：输入框只要有触发到空串的路径，列表就会全量刷出。**最可能被真实用户触发的一条。**

2. **同名/同别名结果取决于数据表插入顺序**
   真实数据中 `congo` / `刚果` / `剛果` 三个别名同时指向 🇨🇩(CD) 与 🇨🇬(CG)。
   `searchRegions` 返回两者（表序 CD、CG），`getRegionByAlias` 只返回表内首个匹配（CD）。
   → 影响：同一别名在不同函数下得到不同答案，且结果由插入顺序决定，非确定性契约。

3. **两种匹配语义并存**
   `isRegionMatch` 是子串匹配（`'hong'` 能命中 `Hong Kong`），
   `getRegionByAlias` 是仅精确匹配（`'hong'` / `'united'` 返回 `null`）。
   → 影响：调用方需清楚知道自己在用哪套语义，否则以为"搜索应该模糊匹配"。

4. **`extractRegionEmojis` 不去重**
   同一段文本里重复出现的旗标会重复返回。调用方若直接用于列表渲染，会出现重复项。

5. **错误处理策略不统一**
   `getRegionCode` / `getEmojiByCode` / `getRegionDisplayName` 对未知名**原样返回入参**
   （不抛错、不返回 null），而 `getRegionByAlias` 返回 `null`。
   → 影响：调用方无法用统一方式判断"没找到"。

## 如果要修（建议做法）

单独立项、单独提交，与重构分开：

- 修 #1 时同步确认所有调用方是否依赖「空串=全量」这个行为（可能有人靠它做"清空筛选即显示全部"）。
- 修 #2 时要定一个确定性的排序规则（例如按 `code` 字典序），并补一条断言锁住它。
- #3 建议统一为「两者都支持子串 + 精确优先」，但这是产品决策，不是重构。
- #4 加去重即可，但要确认没有调用方依赖重复项计数。
- #5 建议统一为「未找到返回 null」，但这会改变现有返回值契约，属于破坏性改动，需同步更新调用方。

以上每条修之前，都必须先确认调用方；现有 422 条断言里已经有一部分会直接报错，
这是好事（说明契约被钉住了），但**不要为了改行为而先改断言**。
